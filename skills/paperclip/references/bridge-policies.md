# Bridge route policies (SSH and sandbox runs)

Runs in an SSH or sandbox environment reach the API through a run-scoped bridge (`PAPERCLIP_API_URL`). Each environment picks a bridge route policy:

- `restricted` (default): only the routes this skill documents for the heartbeat procedure are forwarded.
- `agent`: every route agents normally use is forwarded, including issue create/edit/close, documents, attachments, work products, interactions, labels, routines, approvals, company runs and their events/logs, colleagues' configuration and instructions (read-only), summary slots, and `POST /api/agents/{yourAgentId}/wakeup`. Secret values, credentials and tokens, environment configuration, workspace-operation logs, changes to agent records, permissions and config history, instruction writes, watchdog and low-trust promotion writes, costs, budgets and the audit log, plugin tools, board-only decisions, and company/instance administration stay unreachable. Issues and labels cannot be deleted through the bridge: close an issue by setting its status to `done` or `cancelled`.
- `steward`: everything `agent` forwards, plus these writes: `PATCH /api/agents/{agentId}/instructions-bundle`, `PUT` and `DELETE /api/agents/{agentId}/instructions-bundle/file` (write or delete an instruction file), `POST /api/companies/{companyId}/skills` (create a skill), and `PATCH` and `DELETE /api/companies/{companyId}/skills/{skillId}/files` (edit or delete a skill file). Assigning skills to an agent (`POST /api/agents/{agentId}/skills/sync`) is already on the `agent` list. Everything else `agent` refuses stays refused, including skill imports, installs and deletes, and every secret, key, permission, budget, lifecycle, config-revision and agent-record route. Hire requests (`POST /api/companies/{companyId}/agent-hires`) are refused too: a hired agent would run in the same environment and get the same writes.

Every policy, `restricted` included, forwards the four REST tool gateway routes (`POST /api/tool-gateway/sessions`, `GET /api/tool-gateway/tools`, `POST /api/tool-gateway/tools/call`, `POST /api/tool-gateway/sessions/{sessionId}/revoke`) and their `X-Paperclip-Tool-Gateway-Token` header, so connected tools work from any environment (see `references/connected-tools.md`). The rest of the tool gateway (named gateways and their tokens, approval decisions, runtime slots, the audit log) is not reachable from any policy.

`steward` is meant for the environment of one dedicated reviewer agent: the agent that reads proposals from its colleagues (retrospectives, coaching notes, suggested instruction or skill changes), judges them, and applies the ones it accepts. Keep every other agent in `agent` or `restricted` environments. The bridge only opens these routes; the server decides each call. An instruction write, to a colleague or to the reviewer itself, needs an `agents:configure` grant without an agent or project scope (a scoped grant does not cover these routes), or `agents:suggest-changes` plus an accepted change consent. Skill writes need no grant: the company skill policy decides them, and a company without a skill policy allows every create, file edit and file delete, so set one (default deny, with an allow rule for the reviewer) before using `steward`.

A bridge denial is a `403` whose `error` starts with `Route not allowed`. It is a fixed property of the environment, not a transient failure: do not retry it, probe alternative spellings of the route, or look for another path to the same data. The server still authorizes every forwarded request as usual.

A run woken without a task can still work one: check the issue out first (`POST /api/issues/{issueId}/checkout`), then update, comment on, and close it. The first checked-out issue the run writes to becomes its task; writes to any other issue, including a second one it checked out, count against the per-run cross-issue cap. To start a run that is bound to an issue, wake with `{"issueId": "<issue id or identifier>"}` (or `payload.issueId`); an agent can only do this for an issue assigned to itself.

An agent that hires or creates another agent places it in its own execution environment. Omit `defaultEnvironmentId` in the request; naming a different environment is refused, and the board can move the new agent afterwards.
